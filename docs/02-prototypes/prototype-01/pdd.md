## 2. Prototype 01の目的

Prototype 01は完成版の縮小版ではない。IYASAKAの中心体験が、最小限の仕組みでも成立するかを確認するための試作品である。

検証する中心体験は次のとおり。

> 考える → 設計する → 町が答えを返す

住民、木材、倉庫、建設予定地、建物、道路を用いて、町の自律性、配置による効率差、観察と改善の関係を検証する。

Prototype 01では、コンテンツ量や完成版品質を目指さない。主要仮説を評価でき、次の開発判断へ進める状態を目標とする。

## 3. Vision

IYASAKAは、町と向き合い、考え、選び、育てる、和を題材とした町づくり・運営シミュレーションである。

Prototype 01では、このVisionのうち次の核を対象とする。

- プレイヤーは住民を直接操作せず、環境と配置を通じて町へ影響する
- 住民の自律行動によって町がプレイヤーへ結果を返す
- 観察から問題を見つけ、配置を変え、変化を確かめる
- 忙しさではなく、考えることをゲームプレイにする

完成版のVisionとDesign Pillarsの正本はGDDとする。本書はPrototype 01で検証する範囲だけを定義する。

## 4. Design Pillars

Prototype 01は、GDDで定義された次のDesign Pillarsに従う。

1. 町はプレイヤーの思考が形になったものである
2. プレイヤーは問題に追われるのではなく、問題と向き合う
3. 有意義な創造には余白が必要である
4. システムは選択・変化・感情を生むために存在する
5. 住民は自律し、プレイヤーは環境を設計する
6. 破壊は次の創造の理由にならなければならない
7. リアリティより意味のある選択を優先する
8. 忙しさではなく、思考を途切れさせない

Prototype 01では、これらを完成版相当の規模で実装するのではなく、主要仮説の評価基準として使用する。

Prototype 01は、GDDで定義されたDesign Pillarsに反しないことを前提とする。

Prototype 01で直接検証する対象は次のとおり。

- 住民の自律性
- 配置設計
- 観察
- 問題発見
- 改善思考

完成版相当の規模で全Design Pillarsを検証するものではない。

## 5. 検証仮説

### 5.1 自律する住民によって町に生命を感じられる

住民がプレイヤーから直接操作されず、町に必要な仕事を継続して実行することで、町が自律して動いていると感じられるかを検証する。

確認すること：

- 住民が採取、運搬、建設を直接命令なしで行う
- 住民の行動目的をプレイヤーが読み取れる
- 仕事の完了や失敗後も町の活動が継続する

### 5.2 配置と設計によって町の効率が変化する

木、倉庫、建設予定地、道路の位置関係によって、経路、移動時間、運搬時間、運搬量、建設時間が変化し、配置が意味のある選択になるかを検証する。

確認すること：

- 倉庫位置によって運搬効率が変化する
- 建設予定地によって搬入効率が変化する
- 道路の有無と配置によって経路または移動効率が変化する
- 配置変更前後を比較できる

### 5.3 観察が問題発見と改善思考につながる

住民の移動や物流を観察することで、プレイヤーが問題の原因を発見し、配置の改善を考えられるかを検証する。

確認すること：

- 無駄な移動や長い運搬経路に気付ける
- 物流の停滞や作業の停止に気付ける
- 倉庫、建設予定地、道路を改善手段として認識できる
- 改善後の変化を確認できる

## 6. 横断的成功指標

### 6.1 小さな改善にも認識可能な効果がある

倉庫を数セル移動する、道路を数セル追加するなどの小さな変更でも、経路、時間、運搬量、建設完了時間などに確認可能な差が生じる。

### 6.2 一つの改善が次の改善思考につながる

一つの変更を行った後に、プレイヤーが別の問題または改善候補を発見し、続けて町を調整したくなる。

## 9. Gameplay Loop

1. 町と住民の動きを観察する
2. 資源、移動、物流、建設上の問題を発見する
3. 倉庫、建設予定地、道路の配置を考える
4. 配置または建設を変更する
5. 住民が採取、運搬、建設を行う
6. 町の状態と効率が変化する
7. 変更前後を比較する
8. 次の改善を考える

## 10. Core Loop

> 観察する → 問題を見つける → 配置を変える → 町の反応を確認する → 次の改善を考える

Prototype 01では、木の採取、木材の運搬、建物の建設、道路による効率変化を通してこのCore Loopを検証する。

## 11. Prototype全体像

Prototype 01はPhase 1〜7で構成する。Active Phaseは原則として一つだけとし、現在はPhase 2をActiveとする。

| Phase | 名称 | 到達点 |
|---|---|---|
| Phase 1 | 基盤構築 | 空間、観察、時間操作の基盤が動作する |
| Phase 2 | 住民移動 | 住民1人がグリッド上を移動できる |
| Phase 3 | 仕事システム | 住民が仕事を取得・実行し、競合を防げる |
| Phase 4 | 生活ループ | 採取によって町の活動と資源発生が継続する |
| Phase 5 | 物流 | 木材を倉庫へ運び、距離による差を計測できる |
| Phase 6 | 建築 | 資材を搬入し、建物を完成できる |
| Phase 7 | ゲームループ完成 | 道路と配置改善によるCore Loopを評価できる |

Phase 1〜6では道路による経路コスト補正と移動速度補正を実装しない。道路効果はPhase 7で初めて導入する。

## 15. Phase 4 — 生活ループ

Status: Planned  

### 目的

住民が木を採取し、木材アイテムを発生させる最初の連続した町の活動を成立させる。

- Gather

- 木材アイテムの生成
- 採取後の木の状態変更
- 最低2人の住民による採取

## 16. Phase 5 — 物流

- 木材が消失または二重計上されない

- プレイヤーが効率差と原因を認識できる
- 改善後に次の改善案が生まれる
- Prototype全体のGo / Revise / Pivotを判断できる

## 19. Playtest方針

Prototype 01では完成版品質ではなく、主要仮説を再現可能な条件で検証できることを優先する。

許容するもの：

- 固定テストマップ
- 仮UI、仮アート、仮数値
- デバッグ操作
- 手動リセット
- 後で置き換える単純な構造

最低限守るもの：

- 木材が消失しない
- 木材が二重計上されない
- 定義した主要な失敗ケースにおいて、活動が回復するか、停止理由を確認できる
- 失敗または取消後に対象を再利用できる
- 主要な失敗原因を確認できる
- テスト条件を再現できる
- 次Phaseへ進める

各Phaseでは、正常動作、主要な失敗、完了条件、次Phaseに必要な出力を確認する。

すべてのPhaseは、Unity上で人間による動作確認を完了するまで完了扱いにしない。

Playtest結果、実測値、観察、改善案はPlaytest Log（未作成。Prototype全体のPlaytest開始前に作成予定）に記録し、本書へ追記し続けない。

## 21. Go / Revise / Pivot

### Go

次を総合的に満たす場合、Prototype 01をGoとする。

- 住民が直接命令なしで一連の仕事を行う
- 住民の行動が町の活動として認識できる
- 配置変更によって確認可能な効率差が出る
- プレイヤーが問題と原因を発見できる
- 小さな改善の効果を認識できる
- 改善後に次の改善案が生まれる
- 主要な失敗でシミュレーションが停止しない

### Revise

中心構造は維持できるが、次のような修正が必要な場合はReviseとする。

- 自律行動は成立しているが行動理由が読みにくい
- 配置効果が弱い、または強すぎる
- 道路の複合効果が過大である
- 観察よりデバッグ数値へ依存しすぎる
- 局所的な失敗処理や表示が不足している
- 仮値またはテスト条件の調整で再検証できる

### Pivot

次の場合は中心構造または主要仮説を見直す。

- 住民の自律行動が生命感につながらない
- 仕事と競合防止の仕組みが実用的に成立しない
- 配置変更によって意味のある差が出ない
- 物流の観察が問題発見につながらない
- 道路、倉庫、建設位置の変更が意思決定につながらない
- Reviseを重ねても主要仮説を検証できない

## 22. Open Questions

Version 1.0のActive化時点で、Phase 1 System Specの準備へ進むことを妨げる重大なOpen Questionは確認されていない。

次の項目は、該当Phaseの開始直前に仮値または小規模判断として決定する。完成版仕様として先行確定せず、原則としてOpen Questionsへ大量登録しない。

- Phase 1：テストマップサイズ、カメラ速度、ズーム範囲、時間倍率
- Phase 2：基準移動速度、通行不能セル配置、斜め移動の有無
- Phase 3：検証用の単純な仕事、再試行に関する仮値
- Phase 4：木の配置数、Gather作業時間、木材生成数
- Phase 6：仮建物の名称、見た目、サイズ、必要木材数、Build作業時間
- Phase 7：道路補正の仮値、比較シナリオ、計測時間、改善率の算出方法
- Playtest：参加者、回数、観察記録形式

これらはPhaseごとのImplementation HandoffまたはPlaytest準備で決定する。システム構造やPrototypeのスコープへ影響する新たな未決定事項が発生した場合だけ、[Open Questions](./open-questions.md)に登録する。

## 23. 将来System Specへ分離する対象

System Specは対象Phaseの実装直前に必要なものだけを詳細化する。未着手Phaseの文書はDraftの最小テンプレートに留め、実装判断に使用しない。

| 対象Phase | System Spec | 正本範囲 |
|---|---|---|
| Phase 2 | Pathfinding & Movement | 経路探索、移動、到達不能時の挙動 |
| Phase 3 | Task System | 仕事の管理、取得、Lifecycle |
| Phase 3 | Reservation System | 対象の排他的確保と解放 |
| Phase 3 | Resident FSM | 取得済み仕事の実行状態 |
| Phase 5 | Logistics / Haul | 木材の運搬、所持、倉庫搬入、運搬中断 |
| Phase 6 | Construction | 建設予定地、資材搬入、建設、取消 |
| Phase 7 | Road and Movement Cost | 道路の経路コスト、速度補正、比較条件 |

System Specへ分離する内容：

- Task内部仕様とTask Lifecycle
- TaskManagerの選択・取得処理
- Reservationの取得、解除、競合処理
- Resident FSMの状態遷移
- 経路探索とMovementの内部挙動
- Runtime StateとDefinition Data
- 共通Cleanup処理
- 木材のRuntime上の状態管理
- Construction Siteの内部在庫処理
- 道路補正の適用方法
- デバッグ項目の詳細
- 内部クラス構造、データ構造、実装アルゴリズム
